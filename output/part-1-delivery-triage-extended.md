### How the workstreams were formed

These are analyst-defined delivery slices, not an official Foundation taxonomy. I used four signals together: the board column for delivery stage; the issue or PR title and body for the technical outcome; labels, milestones, and linked repositories for context; and explicit dependencies or release gates for the coordination boundary. I grouped items when they shared a meaningful delivery outcome and a plausible next coordination step, then used the dependency column for work that crosses more than one stream.

The labels support the grouping but do not define it by themselves. `release` and `devops` support Release and CI; the NU7 epic and child links, with `nu-7` as a discovery aid, support NU7; `security` and OSS-Fuzz links support Fuzzing. The `consensus` label and linked P2P/sync PR stacks help identify Mining and synchronization. Milestone 42 is legacy context, not the authoritative NU7 plan. Wallet and operator compatibility is defined by the sidecar, migration-guide, gRPC, and integration-test links rather than one shared label. The NU7 label is incomplete: [#11447](https://github.com/ZcashFoundation/zebra/issues/11447) had no `nu-7` label in the snapshot. Labels therefore do not define the scope by themselves.

The resulting streams answer different TPM questions: Can the software be released? What must be ready for NU7? Can nodes and miners follow the chain? Can wallets and operators use the stack safely? Is security testing maintained? A card can contribute to more than one answer, but it gets one primary stream in the table so the triage remains readable. Board cards can also represent a parent issue and a linked PR separately, so stream counts are not task counts or staffing estimates.
